# PitWolf / OverVolt Project Handoff

This document is the context for the next chat and the next developer working on this project.

## Project identity

The project is evolving from **Pitwall Copilot** into an explainable F1 strategy-analysis product called **OverVolt**. The core question is:

> Can the driver overtake now, and is this the right moment to spend electrical energy?

The product is an engineering decision-support dashboard, not primarily a racing game. It combines historical race telemetry, radio context, derived race features and a clearly labelled simulated energy model.

## Critical data honesty

The current OverVolt dashboard is a UX/demo prototype. Its values are currently hardcoded or simulated. FastF1/OpenF1 data is **not yet connected to this dashboard**.

Do not describe the current values as real telemetry. The next implementation must replace the demo arrays with a cached, processed FastF1/OpenF1 scenario. Until then, use these labels:

- REAL: only values directly loaded from verified historical data
- DERIVED: calculations from real data, such as closing rate or braking intensity
- SIMULATED: energy reserve, deployment cost, recovery estimate and future opportunity value

Actual team battery state-of-charge and proprietary ERS deployment are not public. Never present simulated battery percentages as measured team data.

## Target data pipeline

```text

  -> cleaning and validation

  -> feature engineering

  -> Attack/Save/Delay decision
  -> dashboard explanation
```

## Recommended next steps

1. Create `analytics/` with Python ingestion and feature modules.
2. Fetch one verified historical FastF1 session.
3. Identify and document one overtake window manually.
4. Export a compact scenario JSON with source metadata.
5. Replace the dashboard's synthetic chart arrays with this JSON.
6. Recalculate gap, speed delta, DRS and braking zones from the cached data.
7. Keep the energy layer formula-based and versioned.
8. Add a scrubber that updates all charts and recommendation inputs.
9. Validate against the chosen historical scenario.
10. Add more races only after the first scenario is reliable.

Do not begin with reinforcement learning, a 15-car simulator or live streaming. The first credible demo is one real historical scenario with transparent assumptions.

## Recommended dashboard experience

1. Select race, session, driver, opponent and lap.
2. Scrub to an overtake moment.
3. View synchronized speed, gap, throttle, brake and DRS traces.
4. Inspect the modeled energy panel.
5. Compare Attack, Save and Delay.
6. Change one scenario input, such as DRS or gap.
7. Show the recommendation changing and explain why.

## Main risks

- Missing telemetry in some sessions
- False overtake labels caused by pit stops or penalties
- False precision in simulated energy values
- Regulation assumptions changing over time
- Slow FastF1 downloads
- Training leakage if laps from the same race are split randomly

Mitigations: cache processed data, validate each session, label uncertainty, version assumptions, split evaluation by race and show data provenance in the UI.

## Definition of done for the first real-data milestone

- One cached FastF1 scenario loads in the dashboard
- Speed, gap, throttle, brake and DRS values are real and traceable
- Energy output is visibly marked as modeled
- Attack/Save/Delay uses calculated inputs
- Scrubbing updates all panels
- Recommendation has a short explanation
- Demo can be recorded in under three minutes
